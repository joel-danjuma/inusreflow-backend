## Project status

Implementation is underway, following the phased plan in `docs/Insureflow_Backend_PRD.md`. **Phase 0 (scaffolding & infra)**, **Phase 1 (tenancy/auth/RBAC/onboarding)**, **Phase 2 (policyholders/policies/installments/reminders)**, **Phase 3 (commission engine & ledger foundation)**, **Phase 4 (single payments end-to-end)**, **Phase 5 (bulk payments)**, and **Phase 6 (reconciliation & settlement hardening)** have landed: the FastAPI app boots, `audit_logs` exists, tooling (uv/Alembic/pytest/ruff/mypy/CI) is wired up, insurance companies and brokers can onboard/approve/reject and get their first login, an Insureflow Admin can assign a broker to an insurer (`POST /admin/brokers/{id}/assign-insurer`), brokers can create policyholders/policies with a rolling installment window, flag overdue installments, and send reminders, and the commission/ledger foundation is in place: versioned `commission_configs` (broker → insurance_company → global resolution via `resolve_commission_config`, never updated in place), a swappable kobo-rounding `RoundingStrategy` (`app/services/ledger/rounding.py`, see `docs/adr/0001-kobo-rounding.md`), and `post_ledger_entries` enforcing the `sum(debits) == sum(credits)` invariant — proven by a Hypothesis-driven property test sweep plus direct ledger-balance tests, before any real payment touches it. On top of that foundation, a broker can collect a single premium installment via a Squad Dynamic Virtual Account (`POST /payments`, idempotency-key-protected, no OTP — see `docs/adr/0004-squad-virtual-account-collection.md`); `POST /webhooks/squad` persists every delivery verbatim, verifies the `x-squad-encrypted-body` signature, and independently re-queries Squad before flipping a `Payment`/installment to `success`/`mismatch`/`expired`/`failed`; a successful payment posts a balanced commission-split ledger entry and (if the insurer has a confirmed settlement account via `POST /insurance-companies/{id}/settlement-account`) triggers a real-time Squad transfer payout, recorded in `settlement_payouts` and its own balanced ledger posting — all backed by a `FakeSquadClient` for tests and `HTTPSquadClient` for the real sandbox/live API. Bulk payments reuse that same foundation rather than duplicating it: `POST /payments/bulk` validates every installment belongs to the broker and is unpaid (rejecting the whole request, capped at `Settings.max_bulk_payment_items`, before any DB write or Squad call), mints **one** Squad Dynamic Virtual Account for the combined total, and records one `PaymentBatch` + one `PaymentBatchItem` per installment; on success the same webhook path dispatches into `bulk_payment_service.resolve_batch_outcome`, which fans out to mark every installment paid and posts **one ledger `posting_group_id` per item** (preserving per-policy traceability) while still firing **exactly one** settlement transfer for the batch total — never one per item. `payment_service`/`bulk_payment_service` cross-check each other's in-flight claims on an installment (`Payment.status == 'initiated'` vs. a joined `PaymentBatchItem`/`PaymentBatch`), and both paths share `assert_installment_owned_by` so an installment can never be paid (singly or in bulk) by a broker/insurer that doesn't own it. Phase 6 closes the loop on both sides of that pipeline: `settlement_service.settle_payment` now independently re-queries (`SquadClient.requery_transfer`) every transfer it initiates before recording a final status, rather than trusting `initiate_transfer`'s own response — a still-ambiguous result is stored as a genuine `SettlementPayoutStatus.PENDING`, never guessed into success; `retry_failed_settlement` (exposed only via the Insureflow-Admin-only `POST /settlements/{id}/retry`, gated by the new `RETRY_SETTLEMENT_PAYOUT` permission) always mints a fresh `squad_transfer_ref` chained via `previous_attempt_id`, and rejects a second retry against an attempt that's already been retried (preventing a double payout). `reconciliation_service.reconcile_transactions`, beat-scheduled every `Settings.reconciliation_stale_after_minutes` (default 30 min), catches a `Payment`/`PaymentBatch` stuck `initiated` past that window and resolves it through the *exact same* `payment_service.resolve_payment_outcome`/`bulk_payment_service.resolve_batch_outcome` entry points the webhook path uses — never a separate write path, so a missed webhook is recovered identically to a delivered one. `reconciliation_service.reconcile_transfers` pages Squad's `GET /payout/list` and auto-resolves only `PENDING` payouts to a terminal status; an already-terminal payout that disagrees with Squad's listing is never silently rewritten, only audit-logged (`settlement_payout.reconciliation_mismatch`) for human review — see `docs/adr/0005-reconciliation-scope.md` for the full rationale, including the caveat that `requery_transfer`/`list_transfers`' response shapes are best-effort from public docs (no live sandbox credentials were available to verify). **Phase 7 (security, observability & load hardening)** has also landed, completing the PRD roadmap: every runtime query now goes through a non-superuser `insureflow_app` Postgres role with Row-Level Security policies scoping every tenant-owned table to the `app.current_tenant_id` session GUC (`docs/adr/0006-row-level-security.md`), as real defense-in-depth alongside — not instead of — the existing app-layer tenant scoping; `POST /payments`/`POST /payments/bulk` are Redis-backed rate-limited per-broker and per-IP (`app/core/rate_limit.py`); `anomaly_service.flag_if_anomalous_batch` flags (never blocks) a bulk batch whose item count or value is a large multiple of the broker's own trailing history; `Policyholder.identification_number` and `InsuranceCompany.settlement_account_number` are pgcrypto column-encrypted at rest (`docs/adr/0007-pii-encryption.md`); `tests/security/` now also covers webhook signature tampering/replay and JWT expiry/tampering; a Prometheus `/metrics` endpoint exposes six counters (`payment_outcomes_total`, `payment_batch_outcomes_total`, `webhook_events_total`, `settlement_payout_outcomes_total`, `rate_limit_rejections_total`, `anomaly_flags_total`) alongside `structlog` logging at every terminal payment/webhook/settlement state transition; and a Locust-driven load test (`tests/load/`, `docs/adr/0008-load-testing.md`) empirically validated `Settings.max_bulk_payment_items=500` — which surfaced and fixed a real N+1-query bottleneck in bulk-payment installment validation (~8x latency improvement at the 500-item cap) rather than just tuning the cap number. Secrets-manager integration and audit-log retention remain explicitly provisional/deploy-time decisions, documented but not built (`docs/adr/0009-secrets-management.md`, `docs/adr/0010-audit-log-retention.md`), since neither has a confirmed deploy target or regulatory answer yet. This completes every phase in the original roadmap — check git history / the codebase directly for anything that changes after this point rather than assuming this file stays exhaustive forever.

## What Insureflow is

Insureflow is a multi-tenant platform: insurance companies onboard brokers (many-to-many — a broker can work with several insurers at once and vice versa, `docs/adr/0011-broker-insurer-many-to-many.md`), insurers create policyholders and policies (each policy carries an insurer-supplied, unique `reference_number` debit note), brokers collect premiums (single or bulk) against policies assigned to them via the **Squad** payment gateway, and Insureflow settles funds to the insurer net of a three-way commission split (GTBank / Insureflow / Broker).

Stack: **Python (FastAPI, Pydantic v2), SQLAlchemy 2.0 (async, asyncpg) + Alembic, PostgreSQL, Redis/Celery, Squad (GTBank) Payment API**, dependency-managed with `uv`.

The full spec lives in [docs/Insureflow_Backend_PRD.md](docs/Insureflow_Backend_PRD.md) and the full phased build plan lives in [docs/adr/](docs/adr/) (decision records) — treat the PRD as the source of truth for anything not summarized below, especially the API surface (§10) and security requirements (§11).

Don't assume a column exists just because a later feature will need it; check the actual migration history.

## Core domain model & invariants

These are the non-obvious rules baked into the data model — violating them breaks the product's core promises, so preserve them through any implementation:

- **Multi-tenancy**: scoped at the Insurance Company level. Every query must be filtered by `insurance_company_id` at the service/repository layer via a `TenantScopedRepository` base class. Postgres RLS now backs this as defense-in-depth (`docs/adr/0006-row-level-security.md`): app runtime queries go through the non-superuser `insureflow_app` role, and every tenant-owned table has a policy scoped to the `app.current_tenant_id` session GUC, set per-request by `app/core/deps.py`'s `_set_rls_context`. A second GUC, `app.current_broker_id`, does the equivalent job for a broker actor (`docs/adr/0011-broker-insurer-many-to-many.md`) — never conflate the two; `app.current_tenant_id` is insurer-scoping only, a broker's dashboard counterparty narrowing is always a plain app-layer filter, never written into that GUC. A DB session that never sets either GUC (e.g. a one-off script using `async_session_factory` directly) sees no tenant filter at all — RLS is defense-in-depth on top of correct app-layer scoping, not a substitute for it.
- **Broker–Insurer relationship is many-to-many**: `broker_insurer_assignments(broker_id, insurance_company_id, is_active, ...)`, not a FK on `brokers`, with a partial unique constraint on `(broker_id, insurance_company_id) WHERE is_active = true` — a given pair can't be double-active, but a broker (or insurer) can have many different pairs active at once. `app/core/deps.py::get_tenant_id` no longer resolves a single insurer for a broker actor (see ADR 0011) — don't reintroduce that assumption.
- **Policies are generic at launch**: `policies.policy_type` is an open string seeded with `GENERIC`, not a fixed enum — don't hardcode a closed enum of policy types.
- **"Users" (PRD) vs `PlatformUser` (code)**: the PRD calls policyholders "Users," but that collides with authenticated platform login accounts (admins/brokers need logins; policyholders don't). Internally, the login identity model is `PlatformUser` and the policyholder data record is `Policyholder` — everywhere in code (models/services/repos). The public API path stays `/users` to match PRD §10 literally. Don't reintroduce a `User` model name for either concept; it recreates the ambiguity this split was meant to resolve.
- **Premiums are never auto-debited.** Each due date produces a `premium_installment` row (`status: due`); a broker must explicitly trigger payment. A scheduled job only flags `overdue`, it never charges.
- **Single vs. bulk payments share one mental model**: the broker is debited **once** per action and the insurer is settled **once** per action, net of commission — bulk is "many installments, one debit, one settlement," never repeated single calls. Bulk batches are capped at `MAX_BULK_PAYMENT_ITEMS = 500` (configurable, not Squad-imposed — bounds our own payload/fan-out cost).
- **Idempotency is mandatory** on every payment-initiating endpoint (`POST /payments`, `POST /payments/bulk`) via an `Idempotency-Key` header; replays must return the original result, never a duplicate charge. Squad transaction/transfer references are server-generated as `{merchant_id}_{uuid}`.
- **Webhooks are never trusted blindly**: persist verbatim to `webhook_events`, verify the `x-squad-encrypted-body` signature, process idempotently keyed on `transaction_ref` + `event_type`, and **independently re-verify** via Squad's query/re-query endpoint before any financial state change. A periodic reconciliation job cross-checks Insureflow state against Squad's transaction/transfer listing endpoints.
- **Money is always integer kobo, never floats.** Commission rates are always integer **basis points**, never floats.
- **Commission is versioned, scoped config, not constants.** Resolution order is broker → insurance_company → global (most specific wins), and the resolved config is **locked onto the `Payment`/`PaymentBatch` row at payment time** — later rate changes must never retroactively alter historical transactions. Changing a rate closes the old row (`effective_to = now`) and inserts a new one; never update a commission row in place. Confirmed defaults: GTBank 0.5%, Insureflow 0.5% (broker rate is nullable/insurer-set).
- **Accounting is double-entry**, not balance fields — see the ledger account types in PRD §8.7 (`BROKER_CLEARING`, `GTBANK_REVENUE`, `INSUREFLOW_REVENUE`, `BROKER_COMMISSION`, `INSURER_PAYABLE`, `INSURER_SETTLED`). Every successful payment/batch posts a balanced entry set via `post_ledger_entries`, which asserts `sum(debits) == sum(credits)` per `posting_group_id` before commit — **this is a hard CI gate**, never skip/xfail a financial-invariant test.
- **Kobo-level rounding**: any remainder kobo from splitting a premium by basis points goes to `INSURER_PAYABLE`, implemented as a swappable `RoundingStrategy` (see `docs/adr/0001-kobo-rounding.md`) — **explicitly provisional pending finance sign-off**, not a settled business rule. Don't treat it as final, and don't hardcode the allocation inline outside the strategy.
- **Failed Squad transfers are never retried with the same reference** — a new payout attempt always uses a new reference; the failure is audit-logged.
- **Audit logging is insert-only and immutable** (`app/models/audit.py`, `app/services/audit_service.py`), covering every onboarding approval, commission config change, and financial state transition (actor, action/entity, before/after state, IP, timestamp). Every state-changing service function should call `record_audit_log` in the same DB transaction as the change it describes.
- **Onboarding requires manual Insureflow Admin approval** for both insurance companies and brokers (`pending → approved/rejected`, rejection requires a stored reason).

## Roles (RBAC + tenant scoping)

Four roles, ceiling-of-permission defined in PRD §4: **Insureflow Admin** (platform-wide, cross-tenant), **Insurance Company Admin** (own tenant), **Broker Admin** (own broker org, incl. staff management), **Broker Staff** (own broker org, no staff management). `docs/rbac-matrix.md` is generated from `app/rbac/permissions.py`'s `ROLE_PERMISSIONS` matrix (lands in the auth/tenancy phase) — don't hand-maintain the two separately, they'd drift.

## Settlement mode

Bulk payments **always** settle as one payout per batch. For single payments, **real-time settlement was chosen for this build** (a payout fires immediately after each successful payment) — see `docs/adr/0003-settlement-mode.md`. `insurance_companies.settlement_mode` is reserved as a column so scheduled net settlement can be added per-insurer later without a schema change, but it is not built.

## Security, observability & load hardening (Phase 7)

- **Row-Level Security** (`docs/adr/0006-row-level-security.md`): `Settings.app_database_url` (the non-superuser `insureflow_app` role) is what the app's async engine actually connects as at runtime — a separate, more-restricted connection string than `Settings.database_url`, which Alembic still uses since migrations need to create roles/policies/extensions. RLS policies key off the `app.current_tenant_id` session GUC, set per-request in `app/core/deps.py`.
- **Rate limiting** (`app/core/rate_limit.py`): Redis-backed fixed-window limits on `POST /payments`/`POST /payments/bulk`, per-broker (`Settings.payment_rate_limit_per_broker_per_minute`, default 60/min) and per-IP (`Settings.payment_rate_limit_per_ip_per_minute`, default 120/min) — generous defaults aimed at runaway/abusive automation, not normal bulk broker workflows.
- **Anomaly flagging** (`app/services/anomaly_service.py`): a bulk batch with item count or total value far above the broker's own trailing-history average (`Settings.anomaly_batch_item_count_multiplier`/`anomaly_batch_amount_multiplier`, both default 5x, requires `Settings.anomaly_min_history_batches` prior batches to evaluate) is audit-logged and metric-incremented for human review — it never blocks the payment.
- **PII/bank-detail encryption** (`docs/adr/0007-pii-encryption.md`): `Policyholder.identification_number` and `InsuranceCompany.settlement_account_number` are pgcrypto column-encrypted at rest, keyed by `Settings.pii_encryption_key` (a real deploy must source this from a secrets manager per `docs/adr/0009-secrets-management.md` — never source control).
- **Observability**: `app/core/metrics.py` defines six Prometheus counters exposed unauthenticated at `GET /metrics` (the scraper carries no app JWT) — `payment_outcomes_total`, `payment_batch_outcomes_total`, `webhook_events_total`, `settlement_payout_outcomes_total`, `rate_limit_rejections_total`, `anomaly_flags_total` — each incremented at the exact service-layer call site that decides the corresponding terminal/alert-worthy state, paired with a `structlog` log call at the same site.
- **Load testing** (`docs/adr/0008-load-testing.md`): `tests/load/` (Locust, run manually via the CLI, never via pytest/CI — deliberately separate from the `load` pytest marker scaffolded in Phase 0, since this needed a real HTTP server rather than the in-process test client) empirically validated `Settings.max_bulk_payment_items=500`. The first run surfaced a genuine N+1 query bottleneck in `bulk_payment_service._load_payable_installments` (~8.2s for a 500-item batch); batch-fetching installments/policies in two queries instead of ~2N dropped that to ~1s. The cap itself didn't need to change.
- **Explicitly provisional, deploy-time decisions, not built**: secrets-manager integration (`docs/adr/0009-secrets-management.md` — the env-var contract is locked, provider integration deferred until a deploy target is chosen) and the audit-log retention period (`docs/adr/0010-audit-log-retention.md` — retain indefinitely until regulatory guidance is confirmed, per PRD §14 open question #8).

## Squad integration surfaces

Collection uses Squad's **Direct API** (server-to-server charge, no hosted checkout redirect — explicit preference, not a default). See PRD §15 for the full endpoint list (`transaction/initiate`, transaction query/verify, `payout/account/lookup`, `payout/transfer`, `payout/requery`, `payout/list`). Squad API keys belong in a secrets manager, never in source control or committed env files (`.env` is git-ignored); sandbox and live credentials must stay strictly separated per environment, never co-loaded.
