# ADR 0007: Column-level PII/bank-detail encryption via pgcrypto

## Status
Accepted for this build — two columns, see Consequences for what's deliberately excluded.

## Context
PRD §11.4 asks for encryption at rest for sensitive fields, on top of the transport-level (TLS) and access-level (RBAC, RLS — ADR 0006) controls already in place. Two columns hold genuinely sensitive data today: `Policyholder.identification_number` (a policyholder's national ID/equivalent) and `InsuranceCompany.settlement_account_number` (a bank account number, looked up and confirmed via Squad's Account Lookup API per PRD §8.6). Both are read/written only through Python attribute access today — no SQL-level filtering or `LIKE` search on either column exists anywhere in the codebase (confirmed by grep before this change) — so encrypting them transparently at the ORM boundary has no call sites to rework.

## Decisions
1. **Encryption happens in Postgres, via pgcrypto's `pgp_sym_encrypt`/`pgp_sym_decrypt`, not in Python.** A SQLAlchemy `TypeDecorator` (`app/core/encryption.EncryptedString`) overrides `bind_expression`/`column_expression` to wrap every bound parameter and every column read in the relevant pgcrypto call. The underlying column type is `bytea` (pgcrypto's own output type); the ORM-facing Python type stays `str`. This means every existing query path — `db.get`, `select()`, ORM attribute access, audit-log `before_state`/`after_state` snapshots — transparently sees plaintext, with zero call-site changes beyond the two `mapped_column(...)` type declarations.
2. **The symmetric key is `Settings.pii_encryption_key`**, sourced from env like every other secret in this codebase (`jwt_secret_key`, Squad credentials) — local-dev default committed, real deploys must override via a secrets manager (PRD §11.3's existing posture, not a new exception). `type_coerce(bindvalue, Text())` on the bind side is a Python-only type hint (no SQL `CAST` emitted) — without it, the bind parameter would inherit the column's `impl=LargeBinary` type and asyncpg would attempt to send it as bytes, which `pgp_sym_encrypt(text, text)` rejects.
3. **The Phase-7 migration (`869246395739`) converts both columns from `varchar`/`text` to `bytea`** via `ALTER COLUMN ... TYPE bytea USING pgp_sym_encrypt(col, '<key>')`. Both tables are empty in every environment this has run against — there is no real backfill being proven here, only a safety net for the (currently hypothetical) case of pre-existing plaintext rows. The migration also explicitly `GRANT EXECUTE`s both pgcrypto functions to `insureflow_app` (ADR 0006's restricted runtime role) rather than relying on PUBLIC's default execute privilege staying unrevoked.
4. **Key rotation is explicitly not solved by this ADR.** Changing `Settings.pii_encryption_key` alone would make every existing encrypted row undecryptable — a real rotation requires a data migration that decrypts every row with the old key and re-encrypts with the new one, in the same transaction or with a documented dual-key transition window. This is flagged here rather than built, since there's no real key in production yet to rotate away from.

## Explicitly out of scope this pass
- **Searchable/indexable encryption**: neither column is ever filtered or searched on (confirmed by grep), so no blind-index or deterministic-encryption scheme was needed. If a future feature needs to look up a policyholder by `identification_number`, this scheme does not support it as-is — pgcrypto's symmetric encryption is non-deterministic (each call produces different ciphertext for the same input), so equality filtering in SQL would need a separate mechanism (e.g., a deterministic HMAC side-column), not a plain `WHERE` on the encrypted column.
- **Other fields PRD §11.4 might eventually cover** (e.g., `kyb_metadata` JSONB free text, contact emails): not encrypted — these two columns were the ones explicitly named as sensitive PII/bank detail in the existing codebase comments, not a general sweep of every string column.
- **Key management infrastructure** (KMS integration, automatic rotation): deferred to deploy-time configuration, same posture as Squad credentials.

## Consequences
- A direct `SELECT identification_number FROM policyholders` (e.g., from a DB admin tool, or a future read-replica/BI pipeline) sees only ciphertext bytes — proven by reading the raw column value alongside the ORM-read plaintext in this phase's verification pass.
- Every existing test/service that creates a `Policyholder`/`InsuranceCompany` with these fields continues to work unmodified — the encryption is invisible above the SQLAlchemy Core boundary.
- `tests/security/test_pii_encryption.py` proves both the transparent round-trip (write via ORM, read back via ORM) and the at-rest guarantee (write via ORM, read raw bytes directly via SQL, confirm they're not the plaintext and not trivially decodable without the key).
