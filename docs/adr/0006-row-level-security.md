# ADR 0006: Postgres Row-Level Security (revisiting ADR 0002)

## Status
Accepted for this build — partial scope, see Consequences.

## Context
ADR 0002 deferred RLS entirely to a pre-go-live hardening phase. PRD §11.2 asks for it as additive defense-in-depth behind the existing app-layer `insurance_company_id` scoping (`TenantScopedRepository`, `get_tenant_id`) — never a replacement for it.

A hard blocker had to be solved first: `docker-compose.yml`'s Postgres service boots with `POSTGRES_USER: insureflow`, which the official Postgres image creates as a **superuser**. Superusers (and the owner of a table, absent `FORCE ROW LEVEL SECURITY`) bypass RLS unconditionally — policies would exist but silently do nothing if the app kept connecting as `insureflow`. The fix is a second, genuinely non-superuser role, `insureflow_app`, created by the new migration (`2e2fb138e9eb`) and granted only `SELECT/INSERT/UPDATE/DELETE` on `public` (plus `ALTER DEFAULT PRIVILEGES` so future tables inherit the grant automatically). `Settings.app_database_url` (new) is what the app's runtime engine (`app/core/db.py`) connects with; `Settings.database_url` (unchanged) stays the superuser connection Alembic uses to manage schema, roles, and policies. Both default to the same local Postgres instance, so no docker-compose change was needed — only a CI env var addition (`APP_DATABASE_URL`) so the test/app run against the restricted role there too.

## Decisions

1. **The session-level tenant context is set once per request, inside `get_tenant_id`** (`app/core/deps.py`), via `SELECT set_config('app.current_tenant_id', :tenant_id, true)` — not a literal `SET LOCAL ...` statement, which can't take a bound parameter over asyncpg's extended query protocol. `get_tenant_id` is already a dependency of every tenant-scoped router (`payments`, `payments_bulk`, `installments`, `policies`, `policyholders`, `reminders`, `commission_configs`), so this required touching exactly one function, not every route. `is_local=true` mirrors `SET LOCAL`'s scoping — the value never outlives the request's transaction, so it can't leak onto a pooled connection's next, unrelated request.
2. **An unset GUC means unrestricted**, not denied. `current_setting('app.current_tenant_id', true) IS NULL` is the first branch of every policy's `USING`/`WITH CHECK` clause. This is deliberate: Celery tasks (reconciliation, overdue-flagging, reminders) and the test suite's direct `db_session` fixture usage never go through `get_tenant_id` and never will — they're trusted-internal/test contexts, not attacker-reachable surface, and forcing them to thread a tenant context through would be a much larger, riskier retrofit for no real security benefit. RLS here protects the one path that matters: a buggy or compromised query reachable through the authenticated HTTP API.
3. **Policy scope is intentionally partial — five tables with a direct, non-nullable `insurance_company_id`**: `payments`, `payment_batches`, `policies`, `policyholders`, `settlement_payouts`. Each gets `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY` (the latter closes the table-owner exemption too, belt-and-suspenders alongside the role switch) and one `tenant_isolation` policy:
   ```sql
   USING (
       NULLIF(current_setting('app.current_tenant_id', true), '') IS NULL
       OR insurance_company_id = NULLIF(current_setting('app.current_tenant_id', true), '')::uuid
   )
   ```
   (identical `WITH CHECK`, so a cross-tenant `INSERT`/`UPDATE` is rejected by the database too, not just by app-layer validation). The `NULLIF` matters: an earlier draft cast the raw `current_setting(...)` value inline as a separate `OR`'d branch (`... OR x = '' OR y = x::uuid`), relying on left-to-right short-circuit evaluation to keep `''::uuid` from ever running. Postgres's planner is free to reorder `OR`'d quals by estimated cost, so that cast could still run first and raise `invalid_text_representation` on a legitimate cross-tenant request. Folding the empty-string check into the value itself via `NULLIF` before the cast removes the ordering dependency entirely — caught by `tests/security/test_row_level_security.py`'s unset-context test before this ever reached a real request.

## Explicitly out of scope this pass
- **`commission_configs`, `ledger_accounts`**: `insurance_company_id` is nullable *by design* — a `NULL` row is a legitimate global/platform-revenue row, not a leak, and `commission_configs` additionally has `broker_id`-only scoped rows whose tenant is ambiguous without resolving the broker's current assignment. A correct policy here needs real design work (which column(s), how a global fallback row stays visible to every tenant for `resolve_commission_config`), not a copy-paste of the five-table policy.
- **`premium_installments`, `reminders`, `payment_batch_items`, `ledger_entries`**: no direct `insurance_company_id` column; tenant ownership is only reachable via a join to an already-protected parent (`policies`, `payment_batches`, `ledger_accounts`). A correct policy needs a subquery/`EXISTS` against that parent, which is a well-known Postgres pattern but adds real complexity and its own test burden. None of these tables has a list/read endpoint that doesn't already join through the protected parent today, so the app-layer scoping gap this would close is currently theoretical, not live — deferred to a follow-up rather than rushed.
- **Secrets**: `_APP_ROLE_PASSWORD` in the migration is a local-dev literal, the same posture already taken for `Settings.jwt_secret_key`. A real deploy must rotate it via `ALTER ROLE insureflow_app PASSWORD ...` from whatever secrets manager holds the Squad credentials (PRD §11.3) — not by editing the migration.

## Consequences
- `tests/security/test_row_level_security.py` proves the mechanism directly at the SQL level (connecting as `insureflow_app`, setting the GUC by hand, bypassing the app layer entirely) rather than only through HTTP, since a correct app-layer query and a correct RLS policy are observationally identical from the API — the only way to prove RLS is doing real work is to test the database directly.
- A bug in app-layer scoping on the four deferred-join tables, or on `commission_configs`/`ledger_accounts`, is still caught only by `tests/security/test_tenant_isolation.py`, exactly as before this ADR — no regression, but no new protection there either.
- Revisit scope expansion once a read/list endpoint exists for `ledger_accounts`/`ledger_entries` (none does today) or once `commission_configs`' broker/insurer ambiguity is resolved.
